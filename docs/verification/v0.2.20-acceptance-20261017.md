## 调用范围

- `controls.preset` 新增 `single` 与 `multi`，保留 `balanced`（最多三路）与 `deep`（所选范围）以兼容已保存配置。
- 本地规则：查询命中 `对比|比较|综述|review|compare|benchmark|研究|调研|资料|证据|引用|来源|最新|today|latest|news|202\d` 时多通道，否则单通道。
- 搜索相关性过滤：查询含至少两个有效词时，剔除与查询无词元交集的候选；只有一个有效词但该词是连字符／下划线复合 token 时，按「候选需命中该 token 过半段元」过滤。全部被剔除时返回空 `sources` 并说明「未找到与查询相关的结果」。单个普通词（如 `上海天气`）不做过滤。
- 单通道预设不调用重排、不做官方域名补充检索。

## 两段式提取

自动预设 + `mode: organize` 时先派发第一路：2xx、同目标（允许同资源 HTTPS 升级）、非挑战页、段落 ≥ 400 字符时直接返回原文，不加任何标记；否则升级为多路整理，已取得的这一路并入候选且不重复请求。`single` 预设按用户明确选择原样返回；`fetch.singleChannelEscalate: true` 时才在失败或过薄时升级。

## 判据 1 的口径（单通道只派发一路并原样返回）

判据 1 衡量的是**调用范围与输出忠实度**，不是字符数：

> 单通道预设对目标只派发 1 路请求，输出等于该路返回的原文，不含插件添加的标记。

- 单通道预设的契约是「只派发一路，并原样返回该路正文」（README、DESIGN、`docs/configuration.md` 一致）。对一路结果再做长度裁剪会直接删掉该页真实正文，与「原样返回」相互矛盾，也是本轮唯一会被用户察觉的内容损坏。因此不对单通道做长度治理，**也不承诺第三方引擎表示的字符数**。
- 原「≤ 800 字符」是历史值，不构成本版约束。它衡量不了这条判据：`https://example.com` 的输出长度完全由所选通道的渲染器决定——Firecrawl 渲染得 959 字符（多出的 382 字符是源站 `s.js` 用 `navigator.languages` 注入的六语段落，计划「不改事项」已列明不修），AnySearch 为 156 字符，禁用 Firecrawl 后单通道取到的就是后者。
- 内置 HTTP 抓取该页得 **HTML 源码 577 字符**；按 HTML 解析后的**可见正文 171 字符**。此前记录的「段落 576 字符、单段落块」是把整份 HTML 源码当纯文本喂给分块器得到的产物（整份源码算作 1 个段落），不是正文规模，已废止该数字。
- 577 这条路径在默认配置下取不到：`classifyFetchRoute('https://example.com')` 返回 `dynamic`（`/` 无扩展名、也不在 `staticDomains`），只有显式配置 `fetch.staticDomains` 时才走内置 HTTP 静态抓取。默认 `single` 预设打的是第三方引擎。因此本判据不以内置 HTTP 表示作为验收对象。
- 同一 URL 的多种表示仍可复算：`.scratch/verify-0.2.20/channels/runs-live-order/matrix.json` 的 `example-com/single` 行（Firecrawl 腿 959 字符）；内置 HTTP 的 577 字符需另配 `fetch.staticDomains` 取得。
- 结论：在该口径下，单通道预设只派发一路、原样返回、不添加 `提取来源：` 等标记（由 `test/fetch-two-stage.test.ts` 的「single 预设不裁剪长正文：输出等于该通道返回的原文」钉住）。单通道输出长度等于该通道的表示，不是插件预算。

## 判据 3 的口径（页面级输出上限）

- `controls.maxOutputChars` 的默认值从 100,000 改为 **15,000**，语义从「防爆上限」改为「单页输出上限」；设置页与服务端 schema 同步，范围仍是 1,000–1,000,000，长文部署可调高。
- 只压标记不够：GitHub 仓库页 21,775 字符里，仓库文件清单表占 14,479、段落只占 5,944。因此新增清单类表格裁剪：一行的非空单元格**全部是纯链接**（允许空单元格）、且满足该形态的行占 80% 以上的表格，判为清单，裁到前 20 行、最多 4,000 字符，并在输出里写明「已裁剪 N 个清单类表格」。只要某行有一个单元格带正文、数字或说明，该行就算数据行，整张表原样保留——版本历史表、API 端点表、价格表因此不裁剪。
- 实测（本轮重跑真实链路，GitHub 仓库页）：`auto` 11,272 字符、`multi` 11,246 字符，均低于 15,000；清单表裁剪提示存在；补充片段整节 70 字符。
- 代价：arXiv PDF 这类长文在默认预算下会截断并标 `truncated`（实测 14,922 字符、省略 64 个内容块）。这是「页面级上限」的预期结果，需要全文的部署应显式调高 `controls.maxOutputChars`。

## 地址守卫

`src/address-guard.ts` 使用 `ipaddr.js@2.5.0`（与宿主 `dsh-web-fetch-http` 同版本）。字面量地址直接判定；主机名先解析，任一答案非公网单播即拒绝；解析失败不拦截。`fetch.staticDomains` 显式列出的主机豁免，`fetch.blockPrivateAddresses: false` 关闭守卫。守卫等待解析时受操作信号约束。

## 新增依赖

`ipaddr.js@2.5.0`，MIT，无安装脚本，与宿主使用的版本一致。锁文件已更新，`pnpm install --frozen-lockfile` 可复现。

## 已知限制（发布时仍未闭合）

这些缺陷在 0.2.20 复验中仍可复现，本轮未修，读者不应当把它们当作已解决。

**导航外壳被当作正文返回。** 两段式提取的「够用」判据是整篇文档的普通段落字数（`PROBE_MIN_PARAGRAPH_CHARS = 400`），而视频页、列表页一类目标的页面外壳本身就能超过这个数。实测一个视频页返回 2,071 字符，其中导航占比 69.7%、文章导语不在输出里，`probeVerdict` 仍判够用、`body-thin` 一次都没触发；合成探针（外壳 3,742 字符 / 正文 743 字符）也复现了自动预设只派发第一路、把外壳原样返回、有正文的第二路调用数为 0。修法方向是加「最长单段落 ≥ 300 字符」这类结构条件而不是继续调高阈值——6 个真实样本里导航页最长段落为 57 / 275 字符，真正文为 397 / 576 / 720 / 740，单纯调阈值会误伤正常短页面。

**补充片段预算不参与页面预算竞争。** `SUPPLEMENT_TOTAL_BUDGET_CHARS = 4_000` 是绝对常量，不随 `maxOutputChars` 伸缩。同一份抓取在 15,000 / 30,000 / 100,000 三档上限下输出完全相同，说明瓶颈是这个常量而非页面上限。当参照正文选得偏小时（例如多路里只有一路是干净短文），补充片段会占据输出的大头：实测该配置下机械内容 37.2%，自动预设 59.5%；参照选为大正文时同一页面为 10.8%。

**两列全为链接的数据表仍会被当清单裁剪。** 新的清单判定要求「每行非空单元格全部是纯链接」，因此 API 端点表这类真实数据表只要两列都是链接，仍会被裁到 20 行，调高 `maxOutputChars` 也拿不回来（实测 30 行裁掉 10 行）。这条与「数据表格不裁剪」的承诺仍有距离。

**AnySearch 对部分页面返回乱码。** 澎湃文章的多路结果正文是 `æ¾Žæ¹ƒ` 这类 UTF-8 被当单字节重编码的文本，直连其 `/v1/extract` 拿到的 `content` 本身即如此，属上游数据问题、不是插件解码；Tavily 同页正常。多路整理会选中它当参照，导致该页正文不可读。

**内置 HTTP 路径下空正文的 4xx 仍算成功。** 同一 404 带正文时返回结果并标注状态码，无正文时抛错；但走内置 HTTP 的 404/403 在无正文时仍返回 `(HTTP 404)` 加空正文，不是显式失败。

**全引擎失败的分组口径不完整。** 真实 404/403 目前全部归入「引擎不可用」，没有进入「目标被拒绝」组。
